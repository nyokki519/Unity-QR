# 自分のパスワード変更（本番反映済み）

2026-10-24 JST、利用者の「こっちからも変更できる？」に対応。実本番の制限解除だけの版6639938を基点とした独立ブランチ `feature/self-service-password` に実装し、診断・所有者用再設定・Studio転送の追加コードは含めない。

ログイン後の画面上部「パスワード」から、現在のパスワード・新しいパスワード・確認用の新しいパスワードを入力する。新しい値は既存方針と同じ16〜128文字。変更後は自分の全端末で再ログインする。他の管理者・スタッフ・参加者・イベント・受付履歴は変更しない。

既存セッションから対象ユーザーを特定し、クライアントが送るuserIdや権限は対象選択に使わない。現在値の照合を必須とし、確認不一致・CSRF・未認証・短い値を拒否する。現在値不一致は403の専用コードで返し、まだ有効なログインを誤って破棄しない。試行はアカウント単位で10回/15分に制限し、IP変更でも回避できない。新しいテーブル・マイグレーションは不要。

ハッシュ変更・自分のsession失効・password_changeの監査記録を1トランザクションで実行し、失敗時はすべてrollback。成功時のCookieも失効させる。パスワード値をログ・URL・ブラウザ永続ストレージ・再試行用pending Mapへ保存しない。成功・閉じるボタン・Escapeによる閉じる操作で入力欄を消去する。バックエンドがselfPasswordChange機能をsession応答で示した場合だけボタンを出し、配信途中の世代差も扱う。

全136件（100単体＋9 workerd＋15既存ブラウザ＋8運営ブラウザ＋1 LINEブラウザ＋3パスワードブラウザ）と型検査が成功。Node実HTTPで全役割・対象限定・CSRF・入力拒否・回数制限・rollback、実workerdで永続化・旧session失効・Viewer session保持・IP変更時の回数制限、390pxブラウザで入力・エラー・Escape・再ログイン・他Admin session保持を検証した。独立レビューにCritical/Important指摘なし。

利用者の「いいよ」という本番反映承認後、最新バックアップを取得・別DBへ復元検証し、既存Worker/DO/Secrets/varsを保持してcode/assetsを反映した。公開版は3f9b8de0-64c3-4742-9119-150f63b01c16、実装元は072b481。新しいセッション応答のselfPasswordChange=1とAdminログイン、公開app.js/CSSの実ファイル一致を確認した。サーバー上の秘密値をチャットへ貼らせず、利用者自身が新しい値を変更画面で入力する。

先に承認済みのoperatorだけの復旧は別件として完了済みで、新パスワードによる元コードのAdminログイン確認も成功している。この機能のテストのために本番operatorを再変更してはいない。

## 本番反映の検証

既存DO namespace ID・クラス・バインディング名、Secret名/型と全varsの一致を確認。元から適用済みのmigration tag v1を使い、新しい移行・DB作成はしていない。配信前後のエクスポート対象行は全て同一で、後確認用バックアップが通常仕様で追加したcloud_backup監査1行だけを区別した。全ユーザーのハッシュは変わっていない。検証用セッションはlogout済み。

最初の参照設定では実行世代を確認できず、旧公開版へ戻したことをactive deploymentと旧app.js/CSSで確認。その後、既存クラスの標準ローカル参照と適用済みv1宣言を用いて再配信し、実際のsession応答まで待って成功判定した。最新アップロードのGET script contentと、現在公開中のactive deploymentは同じとは限らないため、rollbackは公開版IDと実ファイルで照合する。

公開先の検証は本番ログイン/APIと静的ファイル照合で実施。画面操作は同一ファイルのローカルChromiumで検証済みであり、公開先へのクラウドブラウザー接続は環境の証明書信頼設定により未確認。パスワード変更そのものは利用者が画面で行うため、自動検証から本番の変更POSTを送信していない。
