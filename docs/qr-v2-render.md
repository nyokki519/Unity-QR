# Render test deployment

`render.yaml` supplies a single Docker web service, Singapore region, Starter plan,
1 GB persistent SQLite disk, generated signing key, and API health check.
Creating it provisions **paid** resources; review Render's current prices before
confirming. No Render account actions or deployments have been performed by Codex.
Automatic deployment is disabled; future changes require an intentional deploy.
The existing GitHub Pages site, Analytics, PASS and DROP remain unchanged.

## Create from Blueprint

1. In Render choose **New → Blueprint**, then `nyokki519/Unity-QR`.
2. Select branch **feature/unity-qr-v2** and Blueprint file `render.yaml`.
3. Review the service and persistent disk costs, then apply the Blueprint.

Render supplies `RENDER_EXTERNAL_URL`; the server uses it automatically when
`RENDER=true` and `QR_ORIGIN` is unset. For a future custom domain, explicitly set
`QR_ORIGIN` to that verified HTTPS origin. HTTP is still rejected in production.
The signing key is generated by Render; do not regenerate it during routine deploys.
The private development test DB is **not** uploaded. The server starts with a new
database on its own disk; test events must be created there after login.

## First Admin (one remaining manual step)

Once the deployment is healthy, open the service's **Shell**. Run the following,
enter a unique password of 16–128 characters when prompted, and keep it in your
password manager. The password input is hidden and is not passed as a command-line
argument. Do not paste it into chat or source code.

```bash
read -r -s -p 'Admin password: ' qr_admin_password
printf '\n'
printf '%s' "$qr_admin_password" | node dist/server/cli.js user operator Admin
unset qr_admin_password
```

Create the account once; the command refuses duplicate usernames. No default or
automatic Admin password is shipped. Open the service's real HTTPS URL followed
by `/ops/`, and log in as `operator` using the password you chose.

## iPhone verification

Create a clearly named test event with its reception window currently open, and
three fictional participants. From a second screen display participant A's issued
QR; on iPhone Safari open `/ops/`, select that event, start the scanner and grant
camera permission. Verify the displayed name and server-confirmed receipt, rescan
to verify duplicate handling, and test manual reception/undo. Check denied camera
permission, background/resume, narrow layout, and interrupted-network recovery.
Run the same flow in the actual LINE browser if operators will use it.

Physical iPhone/LINE and real Render persistence/backup checks remain unverified
until this deployment exists. Local WebKit does not replace these checks.
Use the backup procedures in `qr-v2-operations.md` before opening real reception.
