# 登録イベントの整理

AdminでUnity QRの「イベント管理」を開きます。Staff/Viewerには整理操作を許可しません。

## 手動でまとめる

「イベントをまとめる」→同じ開催日（日本時間）の統合先→人数・同姓同名候補・受付時間/会場/定員の確認→確定、の順で操作します。

参加者IDを維持し、名前だけで同一人物とは判定しません。元の登録・監査記録は残します。元のイベントは非表示になり、旧QRリンクと有効な署名QRは統合先で利用できます。スタッフには統合先の権限を別途付与してください。

統合は元に戻せません。受付/取消履歴があるイベント、別日、定員不足、同一参加者IDの状態不一致は拒否します。確認後に登録/名前/設定が変われば再確認します。統合先の開催日は別日に変更できません。同じLINEに複数の参加者登録が集まる場合、コードなし再取得は運営確認になることがあります。

## 削除・中止と復元

理由を入力して「削除・中止」を確定します。完全削除ではなく、一覧から隠して新規登録・QR発行・受付を停止します。参加者と受付履歴は保持します。

「削除・中止・統合済み」を開き、通常の非表示イベントは理由付きで復元できます。統合元は単独で復元できません。Analytics同期は非表示イベントを保留し、勝手に作り直しません。Googleフォーム/スプレッドシート原本や既存分析は削除しません。

## 保存・公開

既存の監査ログから状態を復元し、schema4に新しい表/列は追加しません。ターゲット欠損/循環のあるバックアップを拒否します。この状態を理解しない古いコードに単純に戻さず、現行コードと検証済みバックアップを維持してください。

Macで最新版feature/sheet-authoritative-receptionを取得し、実バックアップ取得・復元検証付きcloud:updateで公開します。Googleスクリプト/秘密設定の変更は不要です。Analyticsは機能を検出するため、QR更新前も既存同期を継続できます。開発環境から本番DB操作はしていません。

以前誤った参加者名で発行済みのQRは、自動的に名前を変えません。新規申込には受理済みの申込名を使います。既存の名前・受付履歴を一括変更しないための制約です。
